# E5 節點失效、冗餘路徑與移動

## 目的

災難現場的 mesh 不會靜止：中繼者會離開、手機會沒電、救援者會從遠處走進來。這個實驗量測：

1. 中繼消失時會掉多少封包、多久被偵測到、回來後多久恢復。
2. 有冗餘路徑時，flooding 能不能做到不掉封包的切換。
3. 救援者走近時，在多遠的距離開始收到 Health Report。
4. **救援者到達之前送出的 Health Report，之後還收不收得到。**

## 依程式碼推得的預期

- Peer 清單的過期時間為 180 s（`STALE_PEER_TIMEOUT_MS`），斷線寬限期為 10 s（`PEER_DISCONNECT_GRACE_MS`）。中繼消失後，遠端節點的 peer 清單可能還會顯示已經到不了的節點，最多約 3 分鐘。
- [#91](https://github.com/dioispen/cares-mesh-app-android/issues/91) 之後，Health Report 納入 anti-entropy 同步：每個節點保留每個發送者**最新一份** Health Report 2 小時，鄰居連上 1 s 後就會互相補送缺的封包。因此預期：**救援者到達之前送出的 Health Report，救援者連上中繼後數秒內就會收到最新一份**（舊的幾份不補）。
- 例外：接收端要有發送者的 signing key 才收得下補送的回報，而 key 只在發送者最後一次 ANNOUNCE 後約 3 分鐘內拿得到。**發送者已離開 mesh 超過 3 分鐘時，晚到的救援者仍收不到**，待 [#95](https://github.com/dioispen/cares-mesh-app-android/issues/95) 解決。
- #91 之前的版本不同步 Health Report，晚到的救援者只看得到他進入範圍之後才送出的回報。比較新舊資料時要註明版本。
- 7 支手機都在 flooding 區間，有冗餘路徑時，單一路徑斷掉應該不會掉封包。

## 場地與共同設定

- 與 E1 相同的戶外場地。
- 間距 s 取 E1-C 中 N7 PDR ≥ 95% 的最大間距（以下記為 `s*`）。
- 失效時刻與恢復時刻用牆鐘記錄到秒，由專人喊口令並記錄。

## E5-A 中繼失效與恢復：線性鏈（約 60 分鐘）

**佈置**：與 E1-C 相同的 7 機線性鏈，間距 `s*`。

```
N1 ── N2 ── N3 ── [N4] ── N5 ── N6 ── N7
                   ↑ 在 t = 60 s 失效，t = 180 s 恢復
```

**失效方式**（每種做一次 run，有時間的話各做兩次）

| 方式 | 失效時的操作 | 恢復時的操作 | 模擬情境 |
|---|---|---|---|
| F1 | 關閉藍牙 | 打開藍牙 | 使用者誤關、系統異常 |
| F2 | 強制停止 app | 重新打開 app | App 被系統殺掉、沒電關機後再開 |
| F3 | 持 N4 的人往側面走到 2·d_max 以外 | 走回原位 | 中繼者離開 |

**步驟**

1. 拓撲穩定 120 s 後，N1 開始送：TTL 7、間隔 1 s、共 360 筆（6 分鐘）。
2. t = 60 s，N4 依方式失效。
3. t = 180 s，N4 恢復。
4. 從 t = 60 s 開始，N7 的人每 15 s 看一次 peer 清單，記錄 N1 從清單中消失的時間。

**記錄表**

| 方式 | 失效期間 N5–N7 的遺失數 | T_detect (s) | T_recover (s) | 恢復後 30 s 內的額外遺失 | N7 peer 清單的殘留時間 (s) | 備註 |
|---|---|---|---|---|---|---|
| F1 | | | | | | |
| F2 | | | | | | |
| F3 | | | | | | |

- **T_detect**：N3 或 N5 記錄到 N4 的 `LINK_DOWN` 時間 − 失效時刻。
- **T_recover**：N4 恢復時刻 → N7 恢復收到 N1 封包的第一筆 `RX`。
- **Peer 清單殘留時間**：失效時刻 → N7 的 peer 清單中不再出現 N1。這段期間，使用者看到的是一個其實已經到不了的節點。

## E5-B 冗餘路徑（約 30 分鐘）

**佈置**

```
            N2 ──── N4
          ╱            ╲
  N1 (來源)              N6 ──── N7
          ╲            ╱
            N3 ──── N5
```

- 同一條路徑上相鄰節點的間距為 `s*`，上下兩排盡量拉開（目標 > d_max，做不到的話就記錄實際的鄰接關係）。
- 事後以實測的鄰接表確認確實有兩條不相交的路徑。

**步驟**

1. 拓撲穩定後，N1 開始送：TTL 7、間隔 1 s、共 300 筆。
2. t = 60 s：N4 關閉藍牙（單一路徑斷掉）。
3. t = 150 s：N5 也關閉藍牙（兩條路徑都斷掉）。
4. t = 240 s：N4 打開藍牙（恢復一條路徑）。

**記錄表**

| 階段 | 時間區間 | 存活的路徑 | N7 PDR | N7 R_dup | N7 L p50 (ms) | 備註 |
|---|---|---|---|---|---|---|
| 1 | 0–60 s | 上＋下 | | | | |
| 2 | 60–150 s | 只剩下 | | | | |
| 3 | 150–240 s | 無 | | — | — | |
| 4 | 240–300 s | 只剩上 | | | | |

預期：階段 1 的 R_dup ≈ 2（兩條路徑各送來一份）；階段 2 的 PDR ≈ 100%（無縫切換）；階段 3 的 PDR = 0。

## E5-C 救援者走入與走出（約 40 分鐘）

**佈置**：受困者 S 固定在場地一端（地面上或手持，記錄是哪一種），每 10 s 送 1 筆（TTL 3）。從 S 起算，每 10 m 在地上貼一個標記。

**步驟**

1. 救援者 R 從 1.5·d_max 外（確定在範圍外）出發，app 在前景，以正常步行速度（約 1 m/s）走向 S。
2. 另一人跟著 R 走，每經過一個標記就記下牆鐘時間（或用碼錶按分圈），事後整理成 [stations.csv](templates/stations.csv)：每個標記一列，`t_start` 與 `t_end` 都填經過的時間。
3. 走到 S 旁邊停 30 s，接著往回走，直到超出範圍。
4. 事後把 `LINK_UP`、第一筆 `RX`、最後一筆 `RX`、`LINK_DOWN` 的時間對應到距離標記上。
5. 第二次 run：R 的手機放在口袋裡、app 在背景。

**選做**：在 S 與 R 的路徑之間放 N2、N3 兩個中繼（間距 `s*`），看 R 在多遠就能透過多跳收到。

**記錄表**

| Run | R 的狀態 | 中繼 | 走入：LINK_UP 時的距離 (m) | 走入：第一筆 RX 的距離 (m) | 走出：最後一筆 RX 的距離 (m) | 走出：LINK_DOWN 時的距離 (m) | 備註 |
|---|---|---|---|---|---|---|---|
| 1 | 前景手持 | 無 | | | | | |
| 2 | 背景口袋 | 無 | | | | | |
| 3 | 前景手持 | N2、N3 | | | | | |

走入與走出的距離差就是遲滯（hysteresis）：連上需要較近的距離，斷線則發生在較遠處。

## E5-D 晚到的救援者收得到之前的回報嗎（約 30 分鐘）

這個子實驗檢驗 #91 的補送：只送出一次的 Health Report，晚到的救援者收不收得到、要多久。變體 D2 檢驗 #95 尚未解決的限制。

**佈置**：S、N2、N3 排成一條線（間距 `s*`），R 在範圍外。

```
S ── N2 ── N3          R（範圍外，之後走到 N3 旁邊）
```

**步驟**

1. S 用**正常的 Health 畫面**送出 1 筆 Health Report（不用發送器，走真實的使用流程）。
2. 確認 N2、N3 都收到了：看它們的 Health 畫面，或接 USB 跑 `adb logcat -s CARES_EXP | grep ',RX,0x30,'`。現場計數畫面只算實驗 handle，看不到這筆。
3. 等 2 分鐘後，R 走到 N3 旁邊（只在 N3 的範圍內，不在 S 的範圍內），停留 5 分鐘。
4. 檢查 R 的 Health 畫面與 `exp.csv`：有沒有收到 S 的那一筆？有的話，對照 N3 的 `SYNC` 列（`peer` 為 R）確認是同步送達，並記下 R 的 `LINK_UP` 到這筆 `RX` 的時間。
5. **正向對照**：S 再送 1 筆，確認 R 能透過 N3 收到。這是為了排除「R 根本收不到任何東西」的可能。
6. 重複 3 次。

**變體 D2：S 已離開**。步驟 2 之後關閉 S 的藍牙，等 5 分鐘（超過 3 分鐘的 key 期限）再讓 R 走到 N3 旁邊。預期 R 收不到：N3 的 `exp.csv` 會有送給 R 的 `SYNC` 列，R 卻沒有對應的 `RX`（R 沒有 S 的 signing key，封包被丟棄）。這是 #95 的直接證據，#95 解決後應改為收得到。步驟 5 的正向對照改由 N2 送。

**記錄表**

| 重複 | 變體 | N2 有收到 | N3 有收到 | N3 有送給 R 的 `SYNC` | R 收到舊回報（步驟 4） | `LINK_UP` → `RX`（s） | R 收到新回報（步驟 5） | 備註 |
|---|---|---|---|---|---|---|---|---|
| 1 | D | | | | | | | |
| 2 | D | | | | | | | |
| 3 | D | | | | | | | |
| 1 | D2 | | | | | — | | |

**判讀**：變體 D 預期「收到舊回報」全部為是，`LINK_UP` → `RX` 為數秒（連上 1 s 後發出同步請求）。若為否，先確認 N3 有沒有送出 `SYNC`：沒有代表 N3 沒存到 S 的回報；有而 R 沒收下，代表 R 驗不過簽章。變體 D2 預期為否，結果應與 #95 的描述一致。

## 指標總表

| 指標 | 子實驗 | 定義／判讀 |
|---|---|---|
| 失效期間的遺失數 | E5-A | 線性鏈沒有替代路徑，預期全部遺失 |
| T_detect | E5-A | 鄰居多久察覺中繼消失 |
| T_recover | E5-A | 中繼回來後，端到端多久恢復；三種失效方式分開比較 |
| Peer 清單殘留時間 | E5-A | 使用者看到「假在線」的時間 |
| 單一路徑失效時的 PDR | E5-B | 檢驗 flooding 的冗餘能否做到無縫切換 |
| 雙路徑時的 R_dup | E5-B | 冗餘的代價 |
| 走入／走出的距離、遲滯 | E5-C | 救援者實際上要走到多近才看得到受困者 |
| 背景對走入距離的影響 | E5-C | 與 E4-B2 互相印證 |
| 舊回報的補送率 | E5-D | 變體 D 預期 100%（#91）；變體 D2 預期 0%，待 #95 |
| 補送延遲 | E5-D | 救援者 `LINK_UP` 到收到舊回報的時間 |

## 產出

- T_recover、鏈路中斷後的行為 → [calibration-table.md](calibration-table.md)（模擬器的節點流失模型）。
- Peer 清單殘留時間、走入距離 → UI 與救援流程的設計建議。
- E5-D 的結果 → #91 補送的實機驗收（#91 的 AC1）；變體 D2 → #95 的優先順序與驗收依據。
