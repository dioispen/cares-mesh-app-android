# E3 Flooding 耐受度

## 目的

量出純 flooding 在真實 BLE 上的容量：網路在多大負載下開始掉封包、延遲暴增；崩潰後多久恢復；每個封包要付出多少重複傳輸的成本。

依 [ADR-0001](../adr/0001-policy-level-simulation-as-measurement-instrument.md)，7 支手機都在 relay 機率 1.0 的區間，所以這裡量到的是**模擬器的鏈路容量參數**，不是 relay 策略的比較。

## 依程式碼推得的預期

| 項目 | 程式碼中的值 | 預期影響 |
|---|---|---|
| 最大連線數 | 8（`maxConnectionsOverall`） | 7 機團簇中，每支應該有 6 條直連 |
| 每鏈路送出佇列 | 256 筆或 1 MiB（`MAX_PENDING_SENDS_PER_LINK`／`MAX_PENDING_BYTES_PER_LINK`） | 超過就拒收，出現 `BLE send queue full` |
| 廣播 actor 佇列 | 256（`BluetoothPacketBroadcaster`） | 突發時的第一個瓶頸候選 |
| 去重快取 | 10,000 筆，每 5 分鐘清理（`MAX_PROCESSED_MESSAGES`） | 5 分鐘內的唯一封包數接近 10,000 時，會從最舊的開始移除；遲到的重複封包可能被再次接受 |
| Health Report 大小 | Broadcast Tier payload 約 20 bytes | 不會觸發壓縮（> 100 bytes）或分片。本實驗量的是**小封包**的極限 |

**團簇拓撲中每個唯一封包的成本**：來源送出 1 次，6 個鄰居各轉發 1 次（之後再收到的都是重複，會被丟棄），所以：

- C_tx ≈ 7（封包層）
- 每次送出要寫到每條鏈路 → 鏈路層傳輸次數約 7 × 5～6 次
- 每個非來源節點收到約 6 份（1 份 RX + 約 5 份 DUP）→ R_dup ≈ 6

實測值若明顯偏離，代表轉發或去重的行為與程式碼閱讀的理解不同，需要追查。

## 拓撲

**T1 團簇（室內）**：7 支手機放在直徑約 3 m 的圓周上，桌面高度，彼此全部直連。開始前確認每支的直連數都是 6；如果某支不到 6，記錄下來（這本身就是「最大同時連線數」的觀察值）。

**T2 線狀（戶外，選做）**：與 E1-C 相同，間距取 E1-C 中 N7 PDR ≥ 95% 的最大間距。可以排在 E5 那天一起做。

**注意**：手機放在筆電旁邊時，很容易順手插著 USB——**不要插**。插著會切到 PERFORMANCE 模式，結果就無法與其他實驗比較。若因故必須全部接電，就讓 7 支全部接電，並在 runs.csv 註明。

## 自變項

| 變項 | 等級 |
|---|---|
| 每支的發送速率 r | 0.5、1、2、5、10、20 pkt/s（遞增，直到符合停止條件） |
| 同時發送的手機數 k | 1、3、7 |
| 提供負載 λ = k · r | 由上兩者決定 |

## 停止條件（崩潰判定）

符合任一條件就停止往上加負載，並記錄當時的 λ：

- 任一接收端的 PDR < 80%
- p95 延遲 > 10 s
- 出現 app crash 或 ANR
- 出現 `LINK_DOWN`，且 60 s 內沒有恢復

## E3-A 階梯負載（約 60 分鐘）

1. T1 佈置完成，等 120 s，確認每支都有 6 條直連。
2. 依序對 k = 1、3、7：
   1. 對 r 由小到大：所有發送者在**同一個開始時間**以速率 r 送 60 s（N = 60·r），接著靜默 60 s 讓佇列排空。
   2. 每個等級結束後，看現場計數畫面確認沒有觸發停止條件，再進入下一級。
   3. 換下一個 k 之前休息 2 分鐘，確認直連數恢復為 6。
3. 記下 5 分鐘內的累計唯一封包數。接近 10,000 時，特別注意是否出現重複交付（見上方「去重快取」）。

## E3-C 長時間浸泡（30 分鐘）

1. 以 E3-A 量到的 λ_sat 的 50% 作為負載（k = 7，r = 0.5·λ_sat/7），持續 30 分鐘。
2. 開始前與結束後，每支手機接 USB 量一次記憶體：`adb shell dumpsys meminfo com.bitchat.droid`，記錄 TOTAL PSS。量完要拔線。
3. `STAT` 事件會每 60 s 記錄電量、溫度、直連數。

## 指標總表

| 指標 | 子實驗 | 定義／判讀 |
|---|---|---|
| PDR(λ)、L(λ) | E3-A | 負載–效能曲線；找出延遲開始暴增的轉折點 |
| **飽和負載 λ_sat** | E3-A | 所有接收端 PDR ≥ 95%，且 p95 ≤ 2 倍最低負載時 p95 的最大 λ。這是本實驗的主要結果 |
| 單鏈路吞吐 μ_link | E3-A（k = 1） | k = 1 時的飽和速率，近似單一來源可推送的上限 |
| 有效吞吐 goodput | E3-A | 每個接收端每秒收到的唯一封包數 |
| R_dup、C_tx、鏈路層傳輸次數 | E3-A | flooding 的成本，對照上方的預期值 |
| QFULL、LINK_DOWN | E3-A、B、D | 崩潰的形式：是佇列滿、斷線，還是兩者都有 |
| 重複交付 | E3-A、B | 應為 0；不為 0 時，檢查是否與去重快取上限有關 |
| T_drain、恢復時間 | E3-B | 突發後多久能回到正常 |
| 最大同時連線數 c_max | T1 開始前 | 實際觀察到的直連數上限 |
| 記憶體增量、溫度、耗電 | E3-C | 長時間中等負載下是否穩定 |
| 線狀 λ_sat | E3-D | 與團簇比較，量出瓶頸效應 |

## 產出

- λ_sat、μ_link、c_max、Q（佇列上限的實測觸發點）→ [calibration-table.md](calibration-table.md)
- R_dup、C_tx → 「純 flooding 的成本」基準線，模擬器中各種 relay 策略都和這條線比較。
- 崩潰形式、恢復時間、浸泡穩定性 → 實地可用性結論（大量 Health Report 同時湧入時，系統會怎樣失效）。
